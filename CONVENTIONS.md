

- Při `Nullable=disable` neinicializuj referenční vlastnosti jen kvůli nullability, např. nepoužívej `= string.Empty` ani `= null!`. Inicializace kolekcí potřebné pro jejich použití a skutečné provozní výchozí hodnoty zůstávají.

- AuthService nezná DbContext ani EF API a neskládá LINQ databázové dotazy. Používá metody IUserRepository; obsazenost e-mailu včetně smazaných účtů kontroluje UserExistsByEmailAsync. Dotaz a IgnoreQueryFilters patří do implementace repozitáře.
- Repozitáře pouze načítají entity a připravují změny; nemají Commit ani SaveChanges. IUnitOfWork v Base vystavuje SaveChangesAsync, BeginTransactionAsync, CommitTransactionAsync a RollbackTransactionAsync. Implementace v Data drží transakci uvnitř, CommitTransactionAsync uloží změny a potvrdí transakci; rollback odpojí sledované entity, aby se změny po vrácení transakce později neuložily. Ve službách nepoužívej try/catch pro řízení transakcí. AuthService při očekávaném neúspěchu volá rollback před vrácením výsledku; při výjimce vrátí nepotvrzenou transakci UnitOfWork.DisposeAsync při ukončení DI scope. Scoped DI uvolňuje UnitOfWork, které při dispose vrátí případnou nepotvrzenou transakci; sdílený DbContext vlastní a uvolňuje DI. Identity, OpenIddict, repozitáře a UnitOfWork sdílejí jednu scoped instanci kontextu. Identity a OpenIddict si interně ukládají své operace, společnou transakci řídí UnitOfWork. Obal RepositoryTransaction se nepoužívá.
- Nullable ID uživatele při kontrolách načítej do proměnné a ověřuj přes HasValue, nepoužívej vazebný pattern is not { } v podmínce nebo ternárním výrazu. Vnořené asynchronní získání hodnoty pro parametr rozděl do proměnné a následného volání.

- Časy našich entit (CreatedAt a UpdatedAt včetně registrace uživatele) se ukládají jako český místní čas nezávisle na časovém pásmu serveru. Používej CzechTime.Now z Base/Time, který převádí DateTime.UtcNow přes Europe/Prague a respektuje zimní i letní čas; nepoužívej DateTime.Now ani pevný hodinový posun. DateTime a DateTime? na našich entitách implementujících IBaseEntity mapuje společná DateTimeConvention na timestamp without time zone. Konvence je registrovaná přes ConfigureConventions; mapování časů knihovních entit Identity a OpenIddict nemění. Plánovač jobu porovnává okamžiky v UTC a termíny počítá podle nastaveného Europe/Prague.

- OpenIddict používá klíče z AuthOptions místo certifikátů: SigningPrivateKey je PEM RSA privátní klíč (alespoň 2048 bitů), EncryptionKey je Base64 kódovaných 32 náhodných bajtů. Podpisový ani šifrovací klíč nepatří do appsettings souborů v repozitáři, a to ani ve vývoji. SigningPrivateKey a EncryptionKey nastav přes user secrets nebo proměnné prostředí; pro nasazení používej vlastní stabilní klíče. Klíče se při každém startu negenerují a všechny instance musí používat shodné klíče. Změna klíčů bez zachování starých zneplatní již vydané tokeny.

- Články: ArticleEntity dědí ExtendedBaseEntity<int>, ArticleType je enum v Core (Police=1, Firefighters=2, Army=3) a v DB se ukládá jako string. Veřejné GET endpointy /api/v1/articles a /api/v1/articles/{id}. Seznam přijímá FilteredRequest<ArticleFilter> s PageNumber, PageSize, SortBy a SortDirection. ArticleFilter obsahuje pouze Type (ArticleType?) a SearchValue (string). SearchValue hledá podřetězec v Title OR Content bez rozlišení velikosti písmen přes ToLower().Contains(); nejde o sémantické ani PostgreSQL full-text hledání. Soft delete respektuje globální filtr. Pro starší DB zůstává připraven skript PublicSafetyHub.Data/Scripts/001_CreateArticles.sql; EnsureCreated existující schéma neaktualizuje.

- Společný request je PaginationRequest (PageNumber=1, PageSize=20, SortBy, SortDirection=asc) a FilteredRequest<TFilter> s volitelným Filter. Stránkování validuje FluentValidation PaginationRequestValidator v Application/Validators, registrovaný existujícím skenováním validátorů. ArticleService.GetArticlesAsync volá IValidator<PaginationRequest>.ValidateAsync před vytvořením specifikace a voláním repository. Při chybě vrací ResultHelper.Validation s první validační chybou; controller pouze volá službu a převádí výsledek přes ToActionResult. PaginationRequest je prostý request model bez DataAnnotations a IValidatableObject. PaginationRequestValidator hlídá PageNumber >= 1, PageSize 1–100 a offset ((long)PageNumber - 1) * PageSize <= int.MaxValue. Neplatné stránkování se přes ApplicationResult a ToActionResult převede na HTTP 400 ProblemDetails bez volání repository. Ochranné podmínky ApplyPagination a checked výpočet v evaluatoru zůstávají; typ článku se samostatně nevaliduje. Chybějící, prázdný nebo neznámý SortBy znamená řazení podle Id bez validační chyby. PagedResult vrací pouze Items, TotalCount, PageNumber, PageSize. Offset/Size a SortPropertyName/SortDescending už API nepoužívá.
- Používej Query Specification pattern s explicitním, typově bezpečným mapováním filtru na entity a operátory. Filtr se přes AutoMapper přemapuje na properties konkrétní specifikace. Její GetCriteria() pomocí běžných if přidává aktivní Expression<Func<TEntity,bool>> podmínky do seznamu a nakonec seznam vrátí; nepoužívej yield return. Jde o jednoduchou variantu inspirovanou WorkContract API a veřejnými příklady Ardalis, nikoli jejich kopii. Společný základ Specification řeší řazení a stránkování přes ApplyPagination. Tuto metodu volá centrálně BaseRepository.GetPagedAsync; služby předají specifikaci a FilteredRequest, neopakují volání ApplyPagination. Null nullable skaláru nepřidá podmínku, 0 a false jsou aktivní filtry. Null, prázdný string a whitespace nefiltrují; null a prázdná kolekce také nefiltrují. Podmínky se skládají AND; u článků text hledá Title OR Content. Filtry ID, kolekcí, dat ani HasUpdates články nemají. Shoda názvů properties nesmí automaticky určovat filtr. AutoMapper přenáší pouze hodnoty filtru; jejich význam a operátory určuje explicitní GetCriteria(). Nepřidávej reflexní odhadování podmínek, generickou mapovací factory ani třídy specifikací pro jednotlivé properties.
- Repozitáře používají zděděné GetAsync pro ID. GetPagedAsync přijímá specifikaci a PaginationRequest, vrací stránku entit bez projekčního overloadu; stránkování i řazení uchovává specifikace. Společný SpecificationEvaluator přidává Where, OrderBy/ThenBy a teprve potom Skip/Take. Pro TotalCount se spouští criteriaOnly=true bez stránkování a řazení. Nepoužívaná podpora Includes a třída SpecificationOrder jsou odstraněné; pro řazení stačí OrderBy, SortDescending a ThenBy. BaseRepository používá AsNoTracking pro čtení a CountAsync i ToListAsync volá postupně bez předávání CancellationToken. Repository načte stránku entit a služba následně převede PagedResult<TEntity> přes mapper.Map na PagedResult<TModel>. Filtry, řazení a stránkování zůstávají v SQL. V DB dotazu se nesmí používat Compile, IsSatisfiedBy, předčasné ToList nebo AsEnumerable. Jedna konkrétní specifikace řeší celý seznam, nevytvářej specifikaci pro každou property.
- Model entity se jmenuje stejně jako entita bez přípony Entity (ArticleEntity -> Article, UserEntity -> User), pokud uživatel neurčí jinak. Pojmenování explicitních requestů typu RegisterUserRequest zůstává. Pro mapování používej AutoMapper 14.0.0 s profily v Application/Mappings a registrací v Host/BuilderExtensions. Jde o verzi před zavedením licencování ve verzi 15; NuGet aktuálně hlásí NU1903 pro tuto verzi, upozornění nepotlačuj. Mapy používej bez MaxDepth a bez explicitního MemberList.Source, pokud uživatel neurčí jinak.

- Zdroj pro Query Specification + Repository: https://specification.ardalis.com/related-resources/patterns-used.html a podmíněné přidávání Where https://specification.ardalis.com/features/where.html. Query by Example přes reflexi bylo nahrazeno explicitní specifikací dle nového zadání.

- ArticleFilter.Type a ArticleSpecification.Type používají ArticleType?; null znamená bez filtru. Specifikace porovnává přímo ArticleEntity.Type s enumovou hodnotou bez ToString() v databázovém dotazu. ArticleEntity.Type a Article.Type zůstávají ArticleType, databázové mapování HasConversion<string>() se nemění. Query parametr přijímá názvy enumu bez rozlišení velikosti písmen; neznámý název nebo nedefinovaná číselná hodnota vrací při standardním MVC model bindingu HTTP 400.

- Výchozí řazení je Id vzestupně. Specifikace obsahuje explicitní whitelist názvů SortBy a typovaných lambda selectorů; články povolují Id, Title, Type, CreatedAt, UpdatedAt. Chybějící, prázdný nebo neznámý SortBy používá Id bez validační chyby; SortDirection se samostatně nevaliduje, pouze desc zapíná sestupné řazení. U jiného primárního sloupce přidej Id jako jednoznačný ThenBy. Nepoužívej reflexi nad libovolným názvem sloupce od klienta.
- AutoMapper konfigurace je sdílená z DI a profilů Application/Mappings, které načítá AddAutoMapper(typeof(AutomapperProfile)). Profil obsahuje společnou otevřenou mapu PagedResult<> -> PagedResult<>; jednotlivé mapy entit převádějí Items a stránkovací metadata se zachovají.

- Armádu importuje ArmyArticleImportJob v Application každý den v 06:00 a 18:00 v Europe/Prague. Job při startu čeká na další plánovaný čas; aplikace musí běžet. Content obsahuje pouze čistý text RSS description; plný detail článku se nestahuje. Import ukládá nové články jako Army, existující OriginUrl včetně smazaných přeskakuje, již importované články neaktualizuje. Databázové a ostatní neočekávané chyby ukončí dávku a loguje je job; při selhání SaveChanges se neuloží žádný článek z dávky. Souhrn se loguje až po úspěšném uložení. Repository připravuje entity a nastavuje časy, změny ukládá UnitOfWork. Job není trvalá fronta: po odstávce čeká na další plánovaný běh a načte aktuální obsah RSS.
